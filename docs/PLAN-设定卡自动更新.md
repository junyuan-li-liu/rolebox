# 方案：设定卡「自我进化」（提议 + 确认）

> 状态：**待用户确认后实现**
> 记录时间：2026-11-18
> 前提：用户明确 **不做「每个对话独立绑角色」**（太复杂，已放弃）

## 一、想要什么

现在角色设定是死的：写得怎么样，聊一百轮还是怎么样。但实际上聊着聊着，用户会说出一些本该写进设定的事——"我其实不太喜欢被叫老师""我最近在准备专升本""我妈催我考公"。

目标是：**让设定能吸收这些信息，但改不改、改哪儿，由用户说了算。**

## 二、三种做法，以及为什么选中间那个

| 做法 | 体验 | 风险 |
| --- | --- | --- |
| **全自动** | 聊完它自己改，最省事 | 设定会漂移，改坏了不知道从哪一步偏的；每轮还要多一次调用，费用翻倍 |
| **提议 + 确认**（推荐） | 它提建议，你点「采纳」才写入 | 多一点操作，但完全可控，且可回滚 |
| **纯手动** | 你自己看聊天记录手动改 | 最安全，但等于没做这个功能 |

用户原话是"就要建议加确认吧"，所以做第二种。

## 三、触发时机（关键设计）

不做"每轮都判断"——那样每轮多一次 API 调用，又慢又费。

**两个触发口，都归用户控制：**

1. **手动**：角色面板加一个「整理设定」按钮。点一下，拿最近 N 轮对话（默认 20 轮）去分析。
2. **自动提醒（默认关闭）**：设置里可开，每满 N 轮（默认 10 轮）问一次。开启时明确提示"会增加调用次数和费用"。

建议先只做手动那个，用一段时间看效果，再决定要不要开自动。

## 四、交互流程

```
用户点「整理设定」
        ↓
前端取最近 N 轮对话 + 当前角色正文
        ↓
调一次 DeepSeek API（不是主对话，是单独的一次整理请求）
        ↓
返回 JSON：{ change: true/false, additions: [...], reason: "..." }
        ↓
change = false → 提示「这次聊下来没有值得长期记住的新信息」
change = true  → 弹出「建议卡片」：
                  ┌─────────────────────────────┐
                  │ 💡 建议补充到「观澜」的设定      │
                  │                             │
                  │ + 用户在做专升本准备，            │
                  │   压力较大，不希望被反复追问      │
                  │                             │
                  │ 理由：这轮里明确说了两次          │
                  │                             │
                  │ [采纳] [改改再采纳] [忽略]       │
                  └─────────────────────────────┘
        ↓
用户点「采纳」→ 追加到角色正文末尾（带分隔标记），自动存一个历史版本
```

「改改再采纳」= 把建议内容填进编辑框，用户改完再保存。

## 五、技术实现

### 1. 整理用的 prompt（核心）

```
你是设定整理助手。下面是角色的当前设定，以及最近若干轮对话。

任务：判断对话里是否出现了**值得长期记住**的新信息，如果有，写成可以直接
追加到设定里的文字。

只提取这些：
- 用户明确陈述的、长期有效的事实（身份、处境、偏好、关系、底线）
- 用户明确纠正过的对你的称呼或态度

不要提取这些：
- 一次性的情绪、临时任务、当天的安排
- 你自己推测出来的东西
- 用户没说、但你觉得"应该"有的信息

输出严格 JSON：
{"change": true, "additions": ["...", "..."], "reason": "一句话说明依据"}
或
{"change": false, "additions": [], "reason": "..."}
```

要点：**白名单 + 黑名单 + 强制 JSON**，并且"理由"必须能让用户核验。

### 2. 追加方式

不要直接改原文，而是追加一段带标记的内容：

```
（原有设定正文…）

<!-- 以下为后续补充（2026-11-18） -->
- 用户在做专升本准备，压力较大，不希望被反复追问
```

好处：一眼看得出哪些是机器补的，后悔了能整段删掉。

### 3. 历史版本（必须做）

改设定前，把旧版本压进 `localStorage['dsh_role_history_v1']`，保留最近 10 个：

```js
{ roleId, savedAt, content }
```

面板里加「历史版本」，可以查看 + 一键回滚。**没有这个，这个功能不能上线**——改坏了没法救是最糟糕的体验。

### 4. 调用方式

用浏览器直接 fetch DeepSeek API（和主对话同一个 key），`model: 'deepseek-chat'`，`temperature: 0.2`（要稳定，不要发散），`response_format: { type: 'json_object' }`（如果接口支持）。

一次整理的成本：20 轮对话约 3000-5000 token 输入 + 少量输出，按现在的价格几分钱。

### 5. 失败处理

- 返回不是合法 JSON → 提示"整理失败，模型没返回有效结果"，不写入
- 网络错误 → 提示重试
- 返回 `change: true` 但 `additions` 为空 → 当作没有建议

**任何失败都不许静默写入。**

## 六、风险和边界

- **设定膨胀**：聊久了会不停追加，正文越来越长。对策：追加时检查总字数，超过阈值就提示"设定太长了，建议合并精简"，并且整理时可以让它顺便合并同类项（后续再做）。
- **误判**：模型可能把玩笑话当事实。对策：理由必须写清依据，用户能一眼看出"它理解错了"。
- **费用**：手动触发可控；自动触发要明示。
- **隐私**：对话内容会被发给模型——这本来就是聊天在做的事，但要在方案和 README 里写清楚"整理时会把最近 N 轮对话再次发送"。

## 七、工作量

| 部分 | 估计 |
| --- | --- |
| 整理调用 + prompt 调试 | 2 小时 |
| 建议卡片 UI（含"改改再采纳"） | 3 小时 |
| 历史版本 + 回滚 | 2 小时 |
| 失败处理与边界 | 1 小时 |
| 测试（造几段对话验证） | 2 小时 |
| 合计 | **约 1 天** |

## 八、要用户拍板的点

1. **触发方式**：先只做手动「整理设定」按钮，够用吗？还是要连自动提醒一起做？
2. **追加还是覆盖**：建议追加到末尾（可整段删），不改原文——同意吗？
3. **N 取多少**：默认"最近 20 轮"，行不行？
4. **历史版本保留几份**：默认 10 份。
